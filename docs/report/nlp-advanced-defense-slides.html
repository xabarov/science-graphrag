03
Технологический стек

Какие технологии использовались

Стек выбран не ради сложности: каждая технология закрывает отдельный слой системы. Именно сочетание PostgreSQL + Neo4j + Qdrant и агентного runtime поверх графа делает проект GraphRAG-системой, а не обычным RAG-приложением.

Ключевые слои системы

  • Backend и runtime: Python, FastAPI, LangGraph, агент с инструментами.
  • Хранилища: PostgreSQL, Neo4j, Qdrant.
  • NLP pipeline: extraction, embeddings, retrieval, graph query, answer generation.
  • UI и наблюдаемость: React UI, traces, logs, metrics.
  • Оценка качества: P / R / F1, ROUGE-L, latency_p95 и retrieval metrics.
Ключевая инженерная идея здесь не в одной библиотеке, а в сочетании трёх хранилищ, extraction pipeline и agent runtime поверх уже подготовленных данных.
04
Главный инженерный результат

Архитектура системы

Phase 2 на схеме — Agent Runtime: один research-агент и tools к PostgreSQL, Neo4j и Qdrant (не три независимых субагента). При необходимости — надсистемный режим с несколькими специализированными шагами и общей трассировкой.

Почему архитектура устроена именно так

  • Ingest и agent runtime разделены по времени и по смыслу.
  • PostgreSQL хранит операционное состояние и артефакты конвейера.
  • Neo4j — граф знаний и структурные запросы.
  • Qdrant — семантический поиск по чанкам.
  • По умолчанию — один исследовательский контур LLM с привязанным набором инструментов, цикл «вызов инструмента → результат в контекст → снова модель», финал через явный шаг ответа с цитатами.
  • Authorship в графе вынесен в отдельный узел (модель данных ingest-слоя).
Главный инженерный результат проекта — связанная архитектура из двух контуров: ingest-конвейер отдельно готовит данные, а чатовый runtime работает поверх уже построенных хранилищ.

Agent runtime

Инструменты агента и системный промпт

Реестр инструментов для основного исследовательского режима агента. Модель получает имена тулзов, краткие описания и машиночитаемую схему параметров (структурированная валидация, по смыслу как в Pydantic).

Каталог тулзов (9 шт.)
Имя Назначение Слой
cypher_query Read-only Cypher; строки результата для структурных вопросов. graph
edge_search Поиск рёбер / соседей по известному work_id (узел графа). graph
workspace_inspect Статистика workspace, список работ или краткий blurb + sample work_id. catalog
paper_profile Метаданные и авторы одной работы по реальному work_id. catalog
find_works Полнотекстовый поиск работ; с workspace_id или по всему корпусу. catalog
paper_quote_search Семантика по чанкам; quote_candidates для цитирования. evidence
format_bibliography_gost Библиография по списку work_ids в рамках workspace. catalog
idea_search Эмбеддинг-поиск идей по чанкам/работам в Qdrant. retrieval
final_answer Обязательное завершение хода: markdown + список citations. writer

Системный промпт: логика вызова

Контракт (Scope)

Утверждения — только на evidence из workspace (чанки, граф, выводы тулзов). Вопрос вне корпуса — сказать прямо; не выдумывать DOI, метрики, названия. Перед цитированием — сначала найти evidence тулзами.

Маршрутизация (decision table)

  • Инвентарь / обзор — workspace_inspect (stats · papers · blurb); не заменяет полнотекст по названиям.
  • Полнотекст работ — find_works; для «в этом workspace» — тот же workspace_id, что в сообщении; глобальный поиск — без ограничения.
  • Карточка работы — paper_profile только при реальном work_id из find_works, papers/blurb или графа; mode=stats id не отдаёт.
  • Граф — edge_search / cypher_query; для edge_search нужен внутренний work_id — заголовки сначала через find_works.
  • Семантика — idea_search (при необходимости с workspace_id); paper_quote_search — дословные цитаты из чанков.
  • Библиография — format_bibliography_gost только когда уже есть конкретные work_ids в workspace.

Фан-аут и завершение хода

Широкие обзоры: один узкий idea_search или blurb → короткий shortlist работ → один батч paper_profile / paper_quote_search по этим id (без «рваного» фан-аута по многим несвязанным вызовам в одном ходу). Завершение — один вызов final_answer (markdown + citations; пустой список — только с явным объяснением).

Когда тулзы не нужны

Приветствия, мета о возможностях, чисто редакторский ответ без фактов по корпусу.

Итоги

Выводы

Бенчмарки и датасет

  • Одних P/R/F1 и ROUGE-L мало для конвейера с PDF: шум разметки, дефисы, ссылки и список литературы ломают «красивую» цифру без договорённости, как сравниваем с эталоном.
  • В скриптах оценки к метрикам добавляются нормализация текста и эвристики под поле (множества DOI/arXiv, IoU строк для секции References, fuzzy для методов/датасетов, режимы перефраза в эталоне) — иначе бенчмарк не отражает постановку.
  • Параллельно с прогонами нужно периодически смотреть датасет и провальные кейсы, иначе зелёные агрегаты отъезжают от реальности.
  • На старте черновой эталон разумно генерировать сильной LLM по PDF/MD, затем сужать и править вручную — так быстрее выйти на первый покрывающий набор кейсов.

Агент, трассировка, UI

  • Ответ смотреть вместе с трасой шагов; обязательный финальный шаг ответа — типичное хрупкое место при смене промпта или графа (ловит сквозной контрольный прогон).
  • Граф на экране — отдельная задача (масштаб, читаемость), не только корректность данных в Neo4j.

Итоги

Накопленное и дальнейшие планы

Фокус дорожной карты: агентный runtime (инструменты и субагенты), контекст и бенчмарки, продукт — граф в UI, ingestion и дедупликация сущностей.

Runtime

Агенты, субагенты и тулзы

  • База: один исследовательский агент с явным каталогом инструментов к реляционному хранилищу, графу и векторному поиску — без «трёх независимых экспертов» по умолчанию.
  • При усложнении сценариев — маршрутизатор с подзадачами и специализированными шагами при единой трассировке.
  • Tool search по смыслу запроса: меньше лишних вызовов, проще сопровождать рост числа инструментов.
Контекст · оценка

Суммаризация контекста и бенчмарки

  • Уплотнение и суммаризация длинных диалогов: укладываться в окно модели, не терять ранние решения и evidence.
  • Развитие регрессионных наборов и бенчмарков: слои извлечения, сквозной агент, проверки при смене промпта, графа и инструментов — метрики как «договор качества», а не разовый отчёт.
  • Теснее связать прогоны бенчмарков с трассами в UI и провальными кейсами в датасете.
Продукт

Граф, ingestion, дедупликация

  • Движок графа в UI: производительность, подсветка, навигация по большим подграфам без потери читаемости.
  • Ingestion: устойчивость пайплайна (ошибки PDF, таймауты LLM), возобновляемость и прозрачность стадий до записи в хранилища.
  • Дедупликация похожих работ, авторов и извлечённых сущностей — меньше дублей и коллизий в Neo4j и в ответах агента.
Развитие сосредоточено на трёх направлениях: умнее маршрутизировать агента и инструменты, устойчивее вести контекст и бенчмарки, надёжнее строить граф — от загрузки корпуса до экрана.
