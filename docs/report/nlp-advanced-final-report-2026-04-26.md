## Аннотация

В проекте разработана система `Science-GraphRAG` для работы с корпусом научных статей. В отличие от обычного RAG над векторным индексом, система строит граф знаний по статьям, хранит структурированные связи между работами и использует агентный конвейер для ответа на вопросы с обязательными цитатами. Цель проекта состояла не только в извлечении информации из статей, но и в построении проверяемого исследовательского инструмента, поддерживающего запросы, которые плохо сводятся к поиску по косинусной близости: например, поиск предшественников метода, цепочек версий работ или противоречий между публикациями.

Эксперименты проведены на корпусе из 35 статей по object detection. Основные результаты таковы: ночная проверка конвейера извлечения на 30–31 статье проходит без ошибок; retrieval на реальном корпусе стабильно возвращает релевантные фрагменты; многошаговый графовый поиск восстанавливает ключевые цепочки развития методов с recall `0.667`; извлечение утверждений на упрощённом цитатном эталоне даёт `recall=1.0`, однако на более строгом перефразированном эталоне падает до `0.625` на обучающей выборке и `0.25` на отложенной, что выявляет реальные ограничения извлекателя; сквозной агентный режим проходит 10 живых сценариев с `latency_p95=25 983 ms` и средней оценкой судьи `4.8/6`.

Главный результат проекта состоит не только в самой системе GraphRAG, но и в дисциплине её оценки. В программу экспериментов встроены механизмы, которые отделяют реальные проверки от служебных и не позволяют удобным тестам скрывать слабые места системы. Благодаря этому отчёт показывает не только сильные стороны системы, но и её реальные ограничения.

## 1. Введение

### 1.1 Проблема

Поиск по научным статьям часто строится как «векторный индекс + LLM». Для простых фактологических вопросов этого бывает достаточно, однако такая схема плохо работает в трёх типичных ситуациях.

1. Нужно учитывать структуру предметной области, а не только текстовую близость. Вопросы про историю методов, версии работ, связи авторства, датасеты и противоречия между утверждениями естественно выражаются через граф, а не через список похожих фрагментов текста.
2. Нужна проверяемость ответа. Для исследовательского сценария мало получить связный текст: важно видеть, из каких именно статей и фрагментов он собран.
3. Нужна честная оценка качества. Во внутренних ML/NLP проектах контрольные наборы часто оказываются слишком удобными: часть из них воспроизводит заранее зашитый ответ, часть проверяет только форму JSON, а часть случайно совпадает с тем, как эталон был построен.

### 1.2 Цель проекта

Цель проекта состояла в построении сквозной системы для исследователя, работающего с ограниченным, но содержательно связанным корпусом статей. Такая система должна:

- превращать статьи в структурированное представление;
- извлекать сущности и связи, полезные для научного анализа;
- поддерживать и обычный retrieval, и запросы с учётом структуры графа;
- синтезировать ответы с обязательными ссылками на источники;
- оцениваться так, чтобы хорошие метрики действительно означали хорошую работу.

### 1.3 Исследовательские вопросы

В основном тексте рассматриваются четыре вопроса.

1. Можно ли надёжно извлекать из научных статей структуру, достаточную для построения графа знаний?
2. Улучшает ли граф и маршрутизация между агентами работу на запросах, где нужна структура связей между статьями?
3. Насколько убедительны результаты, если исключить контрольные наборы, являющиеся чисто проверочными или структурными?
4. Какие ограничения системы проявляются на более строгих тестах, не допускающих поверхностного копирования ответа из источника?

### 1.4 Что считается вкладом

Вклад проекта состоит из трёх частей.

1. **Системный вклад.** Построен рабочий GraphRAG-конвейер с загрузкой статей, графом знаний, векторным поиском, API, UI и агентным супервизором.
2. **Методический вклад.** Введена схема честной оценки: `trust_signal`, разделение режимов реального и имитированного запуска, двойная/тройная верификация эталонной разметки.
3. **Прикладной вклад.** На корпусе научных статей по object detection показано, что система поддерживает не только поиск по тексту, но и многошаговые запросы, поиск противоречий и структурные связи между работами.

## 2. Система

### 2.1 Общая схема

Система состоит из пяти основных частей:

1. **Конвейер загрузки:** PDF/Markdown/Text преобразуются в нормализованный `article.md`, после чего LLM-стадии извлекают метаданные, авторов, ссылки, методы, датасеты, утверждения и концепты.
2. **Хранилища:** данные раскладываются по трём системам хранения с разной ролью.
3. **GraphRAG runtime:** пользовательский запрос обслуживается агентным супервизором, который решает, когда нужен векторный поиск, когда обход графа, а когда можно формировать ответ.
4. **Интерфейс и API:** система доступна через FastAPI и React UI.
5. **Наблюдаемость:** вызовы LLM и фоновые стадии трассируются через Phoenix/OpenTelemetry.

Кратко конвейер можно записать так:

`PDF → Markdown → структурированное извлечение → Postgres + Neo4j + Qdrant → супервизор → ответ с цитатами`

### 2.2 Почему используется три хранилища

| Хранилище | Роль в системе | Что хранится |
|-----------|----------------|--------------|
| **PostgreSQL** | операционное состояние конвейера | документы, задачи, сырые результаты извлечения |
| **Neo4j** | граф знаний | `Work`, `Author`, `Authorship`, `Method`, `Dataset`, `Claim` и связи между ними |
| **Qdrant** | семантический поиск | эмбеддинги фрагментов, утверждений и работ |

Такое разделение не декоративно. Qdrant хорошо решает задачу «найди релевантные текстовые фрагменты», но плохо отвечает на вопросы вроде «какие работы образуют цепочку развития метода». Neo4j, напротив, подходит именно для структурных запросов. PostgreSQL остаётся источником операционного состояния и вспомогательных артефактов.

### 2.3 Графовая модель

Ключевое архитектурное решение состоит в том, что авторство моделируется не простым ребром `Work → Author`, а отдельным узлом `Authorship`. Это позволяет хранить порядок авторов, аффилиации на момент публикации и делать корректные запросы по истории публикаций.

В графе представлены, в частности, следующие сущности и связи:

- `Work`, `Author`, `Institution`, `Venue`;
- `Method`, `Dataset`, `Claim`, `Concept`, `ResearchTopic`;
- связи `CITES`, `RELATED_VERSION_OF`, `USES_METHOD`, `EVALUATED_ON`, `CONTRADICTS`.

Именно эта модель делает возможными вопросы не только «что написано в статье», но и «как эта статья связана с другими».

### 2.4 Агентный runtime

Вместо одного универсального агента используется супервизор с тремя специализированными агентами:

- `retrieval_agent` работает с Qdrant и текстовым контекстом;
- `graph_agent` выполняет поисковые и Cypher-операции по графу;
- `writer_agent` собирает финальный ответ и обязан возвращать цитаты.

Такое разделение полезно по двум причинам. Во-первых, трасса выполнения становится интерпретируемой: видно, почему система сначала пошла в поиск по тексту, а затем — в граф. Во-вторых, появляется возможность тестировать не только финальный текст ответа, но и саму траекторию решения.

### 2.5 Наблюдаемость и воспроизводимость

Для каждой существенной LLM-стадии создаётся отдельный trace/span (единица трассировки). Это позволяет:

- видеть, где именно тратятся токены и время;
- разбирать сбои конвейера загрузки или агентного runtime пошагово;
- сопоставлять стоимость вызовов с фактическим биллингом.

Для защиты важен не только сам факт наличия наблюдаемости, но и возможность показать, что система воспроизводима и диагностируема, а не является «чёрным ящиком».

## 3. Корпус и дизайн экспериментов

### 3.1 Корпус

Эксперименты проведены на корпусе из **35 статей по object detection**. Этот домен выбран по практической причине: в нём много хорошо известных семейств методов, выраженные связи цитирования, версии моделей и понятные датасеты. Это делает корпус удобным для проверки как retrieval, так и запросов с учётом структуры графа.

В корпус входят:

- семейство YOLO;
- семейство R-CNN;
- одношаговые детекторы (`SSD`, `RetinaNet`, `FCOS`, `ATSS`, `GFL`, `TOOD`);
- методы на основе ключевых точек (`CornerNet`, `CenterNet`);
- методы на основе трансформеров (`DETR`, `Deformable-DETR`, `DINO`, `RT-DETR`);
- классические базовые подходы (`HOG`, `DPM`, `Selective Search`, `OverFeat`).

Такой состав корпуса важен: здесь можно проверять и семантическое сходство, и историческую последовательность методов, и противоречия между архитектурными парадигмами.

### 3.2 Принципы оценки

Чтобы отчёт был читабельным и при этом честным, в основном тексте оставлены только те контрольные сценарии, которые отвечают на исследовательские вопросы из §1.3. Из основного тела исключены:

- чисто контрактные проверки формы ответа (корректность JSON, наличие обязательных полей);
- сценарии с заготовленными ответами, проверяющие форму, а не качество;
- дублирующие обучающие варианты, если они не меняют вывод;
- служебные артефакты, полезные для разработки, но не для внешнего читателя.

Это сознательное решение: для статьи или защиты избыточный список внутренних прогонов только мешает.

### 3.3 Как читать названия экспериментов

Ниже перечислены только основные эксперименты, и для каждого указано, что именно он проверяет.

| Эксперимент | Что проверяет | Как выглядит выход | Основные метрики |
|-------------|---------------|--------------------|------------------|
| **Ночной тест извлечения (`Layer-1 nightly`)** | извлечение метаданных, авторов и ссылок из реальных PDF | структурированные поля и ссылки на публикации | `failed_count` (плюс F1 ссылок в артефактах) |
| **Семантическое извлечение (`Layer-2 semantic`)** | извлечение методов и датасетов | графовые сущности и рёбра `USES_METHOD`, `EVALUATED_ON` | `failed_count` (плюс precision/recall по методам/датасетам) |
| **Поиск с ограничением по набору (`workspace_scoped_live`)** | умеет ли retrieval искать только внутри заданного подмножества статей и корректно отказываться от ответа при нехватке оснований | ответ с цитатами или мотивированный отказ | `forbidden_violation_count`, качество ответа |
| **Гибридный поиск (`hybrid_ablation_live`)** | даёт ли гибридный retrieval полезную выдачу на тематических запросах | ранжированный список релевантных фрагментов | `hit_count`, score, MRR |
| **Многошаговый графовый поиск (`multihop_v2`)** | восстанавливает ли граф цепочки развития работ | упорядоченная цепочка или множество связанных работ | `recall`, `precision` |
| **Строгий тест утверждений (`claims_paraphrase`)** | умеет ли извлекатель находить утверждения, если эталон перефразирован, а не скопирован из статьи | набор утверждений | `recall`, `precision` |
| **Полный агентный сценарий (`agent_tools_live`)** | работает ли супервизор сквозным образом на реальном графе и retrieval | трасса вызовов + ответ с цитатами | оценка судьи, задержка ответа |

Именно эти семь экспериментов используются как основной доказательный материал в отчёте.

### 3.4 Почему отдельно обсуждается честная оценка

Для этого проекта нельзя просто показать среднюю метрику и считать задачу закрытой. Если контрольный набор устроен неосторожно, он может давать хороший результат по построению. Поэтому в проекте введены следующие ограничения:

- каждый контрольный набор помечается `runtime_mode` (`live` — реальный запуск, `canned` — с заготовленными ответами, `mock_runtime` — с имитационными данными, `synthetic_gold` — на синтетическом эталоне);
- имитационные и контрактные проверки не смешиваются с реальными экспериментами;
- часть эталонных наборов проходит двойную или тройную верификацию несколькими независимыми LLM;
- в ряде задач добавлены ограничения против дословного копирования ответа из источника.

Эта методическая часть является одной из главных причин, по которым приведённые ниже результаты можно интерпретировать всерьёз.

### 3.5 Определения всех метрик

Раздел содержит точные определения для каждой метрики, встречающейся в отчёте. Метрики сгруппированы по назначению.

#### 3.5.1 Базовые метрики качества извлечения и классификации

Пусть для некоторой задачи задан **эталонный набор** (gold-набор) — набор правильных ответов, составленный независимо от системы, которую оцениваем. Тогда:

- **True Positive (TP)** — сколько из найденных системой ответов совпадает с эталоном.
- **False Positive (FP)** — сколько из найденных системой ответов отсутствует в эталоне (лишние).
- **False Negative (FN)** — сколько эталонных ответов система не нашла (пропустила).

| Метрика | Формула | Что показывает |
|---------|---------|----------------|
| **Precision** (точность) | TP / (TP + FP) | доля найденного, которая действительно правильна |
| **Recall** (полнота) | TP / (TP + FN) | доля правильных ответов из эталона, которую система нашла |
| **F1** | 2 · Precision · Recall / (Precision + Recall) | гармоническое среднее точности и полноты; 0 — худший результат, 1 — идеальный |

Пример (утверждения, §4.4): эталон содержит 8 утверждений; система нашла 5, из которых 4 действительно присутствуют в эталоне. Тогда TP=4, FP=1, FN=4, Precision=4/5=0.80, Recall=4/8=0.50.

#### 3.5.2 Метрики ранжированного поиска

| Метрика | Формула | Что показывает |
|---------|---------|----------------|
| **hit_count** | число документов из ожидаемого множества, попавших в топ-K выдачи | при hit_count=5/5 все 5 ожидаемых статей вошли в первые K результатов |
| **hit@K** | 1, если хотя бы один ожидаемый документ вошёл в топ-K; 0 иначе | бинарная версия для одного запроса |
| **MRR** (Mean Reciprocal Rank) | (1/\|Q\|) · Σᵢ (1 / rankᵢ) | среднее по запросам обратного ранга первого правильного результата; 1.0 — всегда первое место, 0.5 — всегда второе |

Пример MRR: три запроса, первый правильный результат оказался на позициях 1, 2, 3 соответственно. MRR = (1/1 + 1/2 + 1/3) / 3 ≈ 0.61.

#### 3.5.3 Метрики регрессионного контроля конвейера

| Метрика | Определение | Интерпретация |
|---------|-------------|---------------|
| **failed_count** | число документов, для которых хотя бы одна бинарная проверка (`passed=False`) не прошла | цель — 0; ненулевое значение указывает на регрессию конвейера |
| **forbidden_violation_count** | число случаев, когда в ответ попал документ из-за пределов разрешённого подмножества статей | цель — 0; ненулевое значение означает нарушение границ рабочего пространства |

**Почему `failed_count` для L1/L2, а не только F1?** Ночные проверки устроены как набор бинарных проверок на документ: для каждого PDF проверяются конкретные поля (заголовок, наличие авторов, корректность формата ссылок). `failed_count` считает, на скольких документах хотя бы одна проверка не прошла. Это аналог числа упавших unit-тестов: цель — ноль. Диагностические метрики (F1 по ссылкам, precision/recall по методам) записываются в JSON каждого прогона и используются для сравнения между запусками, но не являются первичным показателем стабилизации конвейера. Смысловая оценка качества извлечения развивается через более строгие наборы (`claims_paraphrase`, multihop, агент).

#### 3.5.4 Метрики кластеризации и согласованности

| Метрика | Определение | Интерпретация |
|---------|-------------|---------------|
| **ARI** (Adjusted Rand Index) | мера совпадения двух разбиений множества на кластеры, скорректированная на случайное совпадение | 1.0 — разбиения идентичны, 0.0 — случайное совпадение, <0 — хуже случайного |

ARI применяется для дедупликации: если одна и та же сущность (например, метод «Focal Loss») встречается под разными написаниями, алгоритм должен объединить их в один кластер. Эталонное разбиение — вручную проверенное, предсказанное — то, что выдаёт алгоритм. ARI измеряет, насколько они совпадают.

#### 3.5.5 Оценка агентного ответа

| Метрика | Определение | Интерпретация |
|---------|-------------|---------------|
| **judge score** | оценка качества ответа системой LLM-as-Judge по шкале 1–6 | 1 — ответ неприемлем, 6 — ответ идеален; оценивается релевантность, обоснованность, наличие и корректность цитат |
| **latency_p95** | 95-й процентиль времени ответа в миллисекундах по всем кейсам | 95% запросов выполнились быстрее этого значения; 5% заняли больше |

Методология оценки судьи: LLM-судья получает вопрос, контекст и ответ системы, но не знает, какая именно модель его сгенерировала. Оценивает ответ по четырём критериям: соответствие вопросу, фактическая обоснованность, наличие цитат, отсутствие галлюцинаций. Итоговый балл — среднее по критериям, округлённое до целого от 1 до 6.

### 3.6 Двухуровневая система оценки: регрессионный контроль и оценка качества

В таблице §3.3 для `Layer-1` и `Layer-2` в качестве основной метрики указан `failed_count`, тогда как для `multihop_v2` и `claims_paraphrase` — `recall` / `precision`. Это не противоречие, а **два уровня измерения**.

1. **Регрессионный контроль (L1, L2).** Ночной набор тестов для базовых слоёв извлечения устроен как *набор бинарных проверок на документ*: для каждого PDF считается `metrics.contract.passed` (L1) или `metrics.passed` (L2). Агрегат — число **проваленных** кейсов: `failed_count`. Интерпретация та же, что у набора автоматических тестов: *«сколько сценариев сломалось?»* Цель — **ноль** падений при стабильном корпусе, а не максимизация одной усреднённой метрики в отчёте.

2. **Оценка качества (retrieval, multihop, claims paraphrase, агент).** Здесь нет жёсткого бинарного контракта «прошёл/упал» как единственного KPI; важна **трактуемая** точность: `recall`/`precision`/`F1`, `hit@k`, MRR, оценка судьи, задержка. Это соответствует постановке «насколько хорошо работает алгоритм при фиксированной задаче?»

**Итог для читателя:** `failed_count` по L1/L2 не заменяет F1 — F1 в артефактах прогонов остаётся, но главный показатель стабилизации конвейера в §4 — число ночных проваленных кейсов. Оценка качества извлечения как смысловой модели дальше развивается через более строгие наборы (`claims_paraphrase`, multihop, агент).

### 4.3 Retrieval на реальном корпусе

#### Retrieval с ограничением по рабочему набору

Эксперимент `workspace_scoped_live` проверяет простой, но важный сценарий: если пользователь работает не со всем корпусом, а только с выбранным подмножеством статей, система не должна подтягивать удобные, но запрещённые документы извне.

Результат `forbidden_violation_count=0` на `6/6` кейсах показывает, что это ограничение выдерживается. Отрицательные сценарии также важны: когда в выбранном наборе нет оснований для ответа, система должна корректно отказываться от ответа, а не выдумывать цитату.

#### Гибридный retrieval

Эксперимент `hybrid_ablation_live` устроен так: системе задаются тематические запросы вроде `anchor-free`, `focal loss`, `set prediction transformer`, и проверяется, попадают ли ожидаемые статьи в топ выдачи. На 8 кейсах наблюдается стабильный `hit_count=5/5`, а верхние значения косинусной близости лежат в диапазоне примерно `0.65–0.74`.

Это хороший знак, но здесь важен честный комментарий. На раннем пилотном корпусе прирост гибридного retrieval над чисто векторным почти не наблюдался (`mrr_delta ≈ 0`). Это не ошибка в таблице, а содержательный вывод: чтобы гибридный поиск начал заметно выигрывать, нужен более разнообразный набор кандидатов. На небольшом корпусе этот эффект может быть слабым.

#### Многошаговый графовый поиск

Эксперимент `multihop_v2` проверяет уже не текстовый retrieval, а способность системы восстанавливать цепочки развития методов через граф. На трёх кейсах получен стабильный `recall≈0.667`.

Этот результат важен именно как подтверждение пользы графа. Одновременно он показывает ограничение текущей реализации: `precision` остаётся низкой (`0.02–0.04`), потому что двухшаговый обход в плотном корпусе вытягивает много лишних соседей. В скрипте `multihop_v2` добавлен опциональный шаг повторного ранжирования соседей-`Work` по косинусной близости эмбеддинга к подсказке из запроса (по умолчанию включён, `--rerank-top-k`), чтобы сократить число ложных соседей до оценки precision/recall. Следовательно, граф полезен как источник структурных кандидатов; при плотном корпусе полезна и последующая фильтрация по семантике запроса.

### 4.4 Извлечение утверждений: почему недостаточно простого эталона

Если смотреть только на `claims production`, можно сделать слишком оптимистичный вывод: `recall=1.0` на 10 кейсах. Но этот контрольный набор основан на цитатном эталоне (gold), где короткая опорная фраза дословно встречается в тексте статьи. Для задачи извлечения это слишком удобная постановка.

Поэтому более важным здесь является эксперимент `claims_paraphrase`, где эталонные утверждения перефразированы и ограничены по перекрытию с исходной статьёй. На нём система показывает:

- обучающая выборка: `recall=0.625`, `precision=0.286`;
- отложенная выборка: `recall=0.25`, `precision=0.077`.

Разрыв между обучающей и отложенной выборками показывает, что часть улучшений на обучающей выборке могла быть следствием косвенной адаптации промптов, а не обобщающей способности системы.

Это один из самых полезных результатов во всём отчёте. Он показывает, что текущий извлекатель действительно умеет находить часть содержательных утверждений, но пока пропускает нетривиально сформулированные случаи и генерирует лишние. Для защиты такой результат лучше, чем искусственная `1.0`: он показывает, что контрольный набор способен различать сильное и слабое поведение.

### 4.5 Сквозной агентный режим

Эксперимент `agent_tools_live` проверяет систему в наиболее близком к пользовательскому режиме сценарии: реальный супервизор, реальный retrieval, реальный граф, финальный ответ с цитатами.

Полученные результаты:

- `10/10` кейсов прошли формальные проверки;
- `latency_p95 = 25 983 ms` (95% запросов завершились быстрее 26 секунд);
- средняя оценка судьи: `4.8/6`.

Этот результат означает, что система уже работает как целостный конвейер, а не набор разрозненных модулей. В то же время задержка около 26 секунд показывает, что функциональная готовность к демонстрации ещё не равна готовности к использованию в реальном режиме. Для снижения задержек без смены модели доступен опциональный эвристический ускоренный маршрут в супервизоре: при `AGENT_SEMANTIC_QUERY_FAST_ROUTE=1` первый шаг маршрутизируется в `retrieval_agent` без лишнего LLM-вызова, если в запросе нет ключевых фраз, характерных для графовых запросов (см. `science_graphrag/agent/graph/supervisor.py`).

### 4.6 Вторичные, но полезные результаты

Некоторые семейства экспериментов не являются центральными для главного тезиса, но подтверждают согласованность всей системы.

1. **Поиск противоречий.** Все 7 проверочных пар были материализованы как связи `:CONTRADICTS` в графе. Это показывает, что слой утверждений и граф действительно связаны между собой, а не существуют независимо.
2. **Дедупликация сущностей.** Для 5 типов сущностей получено качество кластеризации ARI от `0.88` до `1.00`. Это важно, потому что плохая дедупликация быстро разрушает качество графа знаний: один и тот же метод начинает жить под несколькими названиями, а retrieval и обход графа становятся менее надёжными.

Эти результаты полезны как подтверждение того, что система работает не только на центральной цепочке «retrieval → ответ», но и на задачах качества данных.

## 5. Обсуждение

### 5.1 Что доказывают результаты

Если смотреть на результаты в совокупности, проект подтверждает три тезиса.

1. **GraphRAG здесь оправдан.** Система поддерживает запросы, которые неудобно решать только векторным поиском: история методов, противоречия, навигация по корпусу с учётом структуры графа.
2. **Конвейер стабилен на реальном корпусе.** Базовые слои извлечения доведены до ночного состояния без проваленных кейсов.
3. **Оценка не скрывает слабые места.** Как только контрольный набор становится более строгим, это немедленно видно в метриках, особенно на `claims_paraphrase` и многошаговом поиске.

### 5.2 Почему здесь важны не только высокие метрики

Для внешнего читателя может показаться странным, что в отчёте специально оставлены слабые числа вроде `recall=0.25` или низкой precision у многошагового retrieval. Но именно это и делает результаты убедительными.

Если все значения идеальны, а структура контрольных наборов при этом непрозрачна, трудно понять, измеряется ли вообще реальное качество. В данном проекте более низкие метрики играют позитивную роль: они показывают, что контрольный набор действительно отделяет сложные случаи от простых.

### 5.3 Роль честной оценки

Отдельно стоит подчеркнуть, что часть инженерной новизны проекта лежит не в самой LLM-модели, а в способе проверки результатов. В проект были встроены:

- разделение реального и имитационного режимов запуска;
- явная маркировка `trust_signal` (сигнал доверия к результату);
- двойная и тройная верификация эталонной разметки;
- ограничения против тавтологических совпадений для части контрольных наборов.

Для исследовательского программного проекта это существенный вклад. Без таких ограничений итоговые таблицы выглядели бы лучше, но были бы менее надёжными.

## 6. Ограничения

Несмотря на хорошие результаты на части задач, у текущей системы есть явные ограничения.

1. **Доменная узость корпуса.** Все эксперименты проведены на object detection. Это хороший тестовый домен, но он не доказывает переносимость промптов извлечения на другие области науки.
2. **Извлечение утверждений пока слабее, чем хотелось бы.** Строгий перефразированный эталон показывает заметную потерю recall и precision.
3. **Многошаговый retrieval нуждается в постобработке.** Recall уже полезен, но низкая precision мешает напрямую использовать графовый обход как готовый финальный ответ.
4. **Модель-судья и модель-извлекатель частично близки по стеку.** Для оценки в рабочем режиме лучше ещё сильнее разводить модели, которые генерируют ответы и оценивают их.
5. **Сквозная задержка заметна для пользовательского интерфейса.** Система функционально работает, но требует дальнейшей оптимизации маршрутизации и числа LLM-шагов.

Эти ограничения не обнуляют результат проекта, но задают естественный план следующего этапа.

## 7. Заключение

В проекте реализована рабочая GraphRAG-система для научного корпуса с тремя ключевыми свойствами: структурное представление знаний, проверяемые ответы с цитатами и честная система оценки.

Главный вывод состоит в том, что граф знаний и маршрутизация между специализированными агентами действительно полезны для исследовательского сценария, но только при условии, что программа оценки устроена строго и не скрывает слабые места. В этом смысле проект показывает не только инженерную реализацию, но и методологию оценки таких систем.

На защите имеет смысл делать акцент на трёх тезисах:

1. система работает сквозным образом на реальном корпусе статей;
2. она поддерживает типы запросов, которые неудобны для обычного векторного RAG;
3. её качество оценивается не по удобным контрактным тестам, а по реальным и частично «неудобным» контрольным сценариям.

## Приложение A. Что вынесено из основного текста

Ниже перечислены материалы, которые сохранены в репозитории для воспроизводимости, но не обсуждаются подробно в основном теле отчёта.

### A.1 Служебные и контрактные контрольные наборы

Сюда относятся:

- контрольные наборы с заготовленными ответами (canned) и с имитационными данными (mock);
- структурные сценарии проверки формата ответа;
- узкие проверки работоспособности отдельных скриптов запуска;
- промежуточные обучающие и минимальные артефакты, не меняющие основной вывод.

Их наличие полезно для разработки, но они не являются главным доказательством качества системы и поэтому не перегружают основной текст.

### A.2 Где смотреть полные артефакты

- агрегированные результаты: `eval/results/benchmark-metrics-summary.json`
- человекочитаемая сводка: `eval/results/benchmark-metrics-summary.md`
- базис доверия: `eval/results/benchmark-trust-baseline.json`
- сравнение моделей (мультимодельный агрегат): `eval/results/multimodel/summary.json`
- результаты по каждому модулю: `eval/results/current-*.json`
- эталонные наборы: `tests/fixtures/benchmarks/`

### A.3 Какие дополнительные семейства есть в проекте

В репозитории также присутствуют дополнительные контрольные наборы, проверки по концептам и ссылкам, а также вспомогательные артефакты для анализа качества. Они важны для полной инженерной картины проекта, но вторичны по отношению к главному исследовательскому тезису и поэтому оставлены за пределами основного повествования.
