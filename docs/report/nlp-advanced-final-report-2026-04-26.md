## Аннотация

В проекте разработана система `Science-GraphRAG` для работы с корпусом научных статей. В отличие от обычного RAG над векторным индексом, система строит граф знаний по статьям, хранит структурированные связи между работами и использует агентный пайплайн для ответа на вопросы с обязательными цитатами. Цель проекта состояла не только в извлечении информации из статей, но и в построении проверяемого исследовательского инструмента, поддерживающего запросы, которые плохо сводятся к поиску по косинусной близости: например, поиск предшественников метода, цепочек версий работ или противоречий между публикациями.

Эксперименты проведены на корпусе из 35 статей по object detection. Основные результаты таковы: nightly-проверка extraction-пайплайна на 30-31 статьях проходит без ошибок; retrieval на живом корпусе стабильно возвращает релевантные фрагменты; multi-hop graph retrieval восстанавливает ключевые цепочки развития методов с recall `0.667`; extraction of claims на упрощённом quote-based gold даёт `recall=1.0`, но на более строгом paraphrase-gold падает до `0.625` на pilot и `0.25` на holdout, что выявляет реальные ограничения текущего extractor'а; end-to-end агентный режим проходит 10 живых сценариев с `latency_p95=25 983 ms` и средней judge-оценкой `4.8/6`.

Главный результат проекта состоит не только в самой системе GraphRAG, но и в дисциплине её оценки. В программу экспериментов встроены механизмы, которые отделяют реальные проверки от служебных и не позволяют удобным тестам скрывать слабые места системы. Благодаря этому отчёт показывает не только сильные стороны системы, но и её реальные ограничения.

## 1. Введение

### 1.1 Проблема

Поиск по научным статьям часто строится как "векторный индекс + LLM". Для простых фактологических вопросов этого бывает достаточно, однако такая схема плохо работает в трёх типичных ситуациях.

1. Нужно учитывать структуру предметной области, а не только текстовую близость. Вопросы про lineage методов, версии работ, связи авторства, датасеты и противоречия между утверждениями естественно выражаются через граф, а не через список похожих чанков.
2. Нужна проверяемость ответа. Для исследовательского сценария мало получить связный текст: важно видеть, из каких именно статей и фрагментов он собран.
3. Нужна честная оценка качества. Во внутренних ML/NLP проектах benchmark-наборы часто оказываются слишком удобными: часть из них воспроизводит заранее зашитый ответ, часть проверяет только форму JSON, а часть случайно совпадает с тем, как gold был построен.

### 1.2 Цель проекта

Цель проекта состояла в построении end-to-end системы для исследователя, работающего с ограниченным, но содержательно связанным корпусом статей. Такая система должна:

- превращать статьи в структурированное представление;
- извлекать сущности и связи, полезные для научного анализа;
- поддерживать и обычный retrieval, и graph-aware запросы;
- синтезировать ответы с обязательными ссылками на источники;
- оцениваться так, чтобы хорошие метрики действительно означали хорошую работу.

### 1.3 Исследовательские вопросы

В основном тексте рассматриваются четыре вопроса.

1. Можно ли надёжно извлекать из научных статей структуру, достаточную для построения графа знаний?
2. Улучшает ли граф и маршрутизация между агентами работу на запросах, где нужна структура связей между статьями?
3. Насколько убедительны результаты, если исключить benchmark-наборы, которые являются только контрактными или smoke-проверками?
4. Какие ограничения системы проявляются на более строгих тестах, не допускающих поверхностного копирования ответа из источника?

### 1.4 Что считается вкладом

Вклад проекта состоит из трёх частей.

1. **Системный вклад.** Построен рабочий GraphRAG-пайплайн с ingestion, графом знаний, векторным поиском, API, UI и агентным supervisor.
2. **Методический вклад.** Введена схема честной оценки: `trust_signal`, разделение live и mock режимов, dual/triple validation gold-разметки.
3. **Прикладной вклад.** На корпусе научных статей по object detection показано, что система поддерживает не только retrieval по тексту, но и multi-hop запросы, поиск противоречий и структурные связи между работами.

## 2. Система

### 2.1 Общая схема

Система состоит из пяти основных частей:

1. **Ingestion pipeline**: PDF/Markdown/Text преобразуются в нормализованный `article.md`, после чего LLM-стадии извлекают метаданные, авторов, ссылки, методы, датасеты, claims и концепты.
2. **Хранилища**: данные раскладываются по трём системам хранения с разной ролью.
3. **GraphRAG runtime**: пользовательский запрос обслуживается агентным supervisor, который решает, когда нужен vector retrieval, когда graph traversal, а когда можно формировать ответ.
4. **Интерфейс и API**: система доступна через FastAPI и React UI.
5. **Observability**: вызовы LLM и фоновые стадии трассируются через Phoenix/OpenTelemetry.

Кратко пайплайн можно записать так:

`PDF -> Markdown -> structured extraction -> Postgres + Neo4j + Qdrant -> supervisor -> cited answer`

### 2.2 Почему используется три хранилища

| Хранилище | Роль в системе | Что хранится |
|-----------|----------------|--------------|
| **PostgreSQL** | операционное состояние пайплайна | документы, jobs, сырые extraction outputs |
| **Neo4j** | граф знаний | `Work`, `Author`, `Authorship`, `Method`, `Dataset`, `Claim` и связи между ними |
| **Qdrant** | семантический поиск | эмбеддинги чанков, claims и works |

Такое разделение не декоративно. Qdrant хорошо решает задачу "найди релевантные текстовые фрагменты", но плохо отвечает на вопросы вроде "какие работы образуют цепочку развития метода". Neo4j, напротив, подходит именно для структурных запросов. PostgreSQL остаётся источником операционного состояния и вспомогательных артефактов.

### 2.3 Графовая модель

Ключевое архитектурное решение состоит в том, что авторство моделируется не простым ребром `Work -> Author`, а отдельным узлом `Authorship`. Это позволяет хранить порядок авторов, аффилиации на момент публикации и делать корректные запросы по истории публикаций.

В графе представлены, в частности, следующие сущности и связи:

- `Work`, `Author`, `Institution`, `Venue`;
- `Method`, `Dataset`, `Claim`, `Concept`, `ResearchTopic`;
- связи `CITES`, `RELATED_VERSION_OF`, `USES_METHOD`, `EVALUATED_ON`, `CONTRADICTS`.

Именно эта модель делает возможными вопросы не только "что написано в статье", но и "как эта статья связана с другими".

### 2.4 Агентный runtime

Вместо одного универсального агента используется supervisor с тремя специалистами:

- `retrieval_agent` работает с Qdrant и текстовым контекстом;
- `graph_agent` выполняет поисковые и Cypher-операции по графу;
- `writer_agent` собирает финальный ответ и обязан возвращать цитаты.

Такое разделение полезно по двум причинам. Во-первых, трасса выполнения становится интерпретируемой: видно, почему система сначала пошла в retrieval, а затем в graph. Во-вторых, появляется возможность тестировать не только финальный текст ответа, но и саму траекторию решения.

### 2.5 Наблюдаемость и воспроизводимость

Для каждой существенной LLM-стадии создаётся отдельный trace/span. Это позволяет:

- видеть, где именно тратятся токены и время;
- разбирать сбои ingestion или agent runtime по шагам;
- сопоставлять стоимость вызовов с фактическим биллингом.

Для защиты важен не только сам факт наличия observability, но и возможность показать, что система воспроизводима и диагностируема, а не является "чёрным ящиком".

## 3. Корпус и дизайн экспериментов

### 3.1 Корпус

Эксперименты проведены на корпусе из **35 статей по object detection**. Этот домен выбран по практической причине: в нём много хорошо известных семейств методов, выраженные связи цитирования, версии моделей и понятные датасеты. Это делает корпус удобным для проверки как retrieval, так и graph-aware сценариев.

В корпус входят:

- семейство YOLO;
- семейство R-CNN;
- одношаговые детекторы (`SSD`, `RetinaNet`, `FCOS`, `ATSS`, `GFL`, `TOOD`);
- keypoint-based методы (`CornerNet`, `CenterNet`);
- transformer-based методы (`DETR`, `Deformable-DETR`, `DINO`, `RT-DETR`);
- классические baseline-подходы (`HOG`, `DPM`, `Selective Search`, `OverFeat`).

Такой состав корпуса важен: здесь можно проверять и семантическое сходство, и lineage методов, и противоречия между архитектурными парадигмами.

### 3.2 Принципы оценки

Чтобы отчёт был читабельным и при этом честным, в основном тексте оставлены только те benchmark-сценарии, которые отвечают на исследовательские вопросы из §1.3. Из основного тела исключены:

- чисто контрактные smoke-тесты;
- mock/canned семейства, проверяющие форму, а не качество;
- дублирующие pilot/mini-suite варианты, если они не меняют вывод;
- служебные артефакты, полезные для разработки, но не для внешнего читателя.

Это сознательное решение: для статьи или защиты избыточный список внутренних прогонов только мешает.

### 3.3 Как читать названия benchmark-семейств

Ниже перечислены только основные эксперименты, и для каждого указано, что именно он проверяет.

| Эксперимент | Что проверяет | Как выглядит выход | Основные метрики |
|-------------|---------------|--------------------|------------------|
| **Ночной тест извлечения (`Layer-1 nightly`)** | извлечение метаданных, авторов и ссылок из реальных PDF | структурированные поля и citation links | `failed_count` |
| **Семантическое извлечение (`Layer-2 semantic`)** | извлечение методов и датасетов | графовые сущности и рёбра `USES_METHOD`, `EVALUATED_ON` | `failed_count` |
| **Поиск внутри рабочего набора (`workspace_scoped_live`)** | умеет ли retrieval искать только внутри заданного workspace и корректно отказываться от ответа при нехватке оснований | ответ с цитатами или осмысленный отказ | `forbidden_violation_count`, answer quality |
| **Гибридный поиск (`hybrid_ablation_live`)** | даёт ли гибридный retrieval полезную живую выдачу на тематических запросах | ранжированный список релевантных фрагментов | `hit_count`, score, MRR |
| **Многошаговый графовый поиск (`multihop_v2`)** | восстанавливает ли граф цепочки развития работ | ordered chain или set related works | `recall`, `precision` |
| **Строгий тест claims (`claims_paraphrase`)** | умеет ли extractor находить утверждения, если gold перефразирован, а не скопирован из статьи | набор claims | `recall`, `precision` |
| **Полный агентный сценарий (`agent_tools_live`)** | работает ли supervisor end-to-end на живом графе и retrieval | `tool_trace` + cited answer | judge score, latency |

Именно эти семь экспериментов используются как основной доказательный материал в отчёте.

### 3.4 Почему отдельно обсуждается честная оценка

Для этого проекта нельзя просто показать среднюю метрику и считать задачу закрытой. Если benchmark устроен неосторожно, он может давать "зелёный" результат по построению. Поэтому в проекте введены следующие ограничения:

- каждый benchmark-family помечается `runtime_mode` (`live`, `canned`, `mock_runtime`, `synthetic_gold`);
- mock и contract проверки не смешиваются с живыми экспериментами;
- часть gold-наборов проходит dual/triple validation несколькими независимыми LLM;
- в ряде задач добавлены ограничения против дословного копирования из источника.

Эта методическая часть является одной из главных причин, по которым приведённые ниже результаты можно интерпретировать всерьёз.

### 4.1 Сводная таблица

| Эксперимент | Основной результат | Интерпретация |
|-------------|--------------------|---------------|

| **Layer-2 semantic** | `0/31` failures | semantic extraction методов и датасетов работает без nightly-регрессий |
| **workspace_scoped_live** | `6/6` passed, `forbidden_violation_count=0` | retrieval соблюдает границы workspace и корректно отказывается от ответа вне области данных |

### 4.2 Extraction pipeline

Самый важный практический результат ingestion-части состоит в том, что два базовых слоя extraction были доведены до стабильного nightly-состояния:

- для **Layer 1** число failures снизилось с `18/30` до `0/30`;
- для **Layer 2** число failures снизилось с `7/31` до `0/31`.

Это означает не просто "LLM иногда возвращает похожий JSON", а то, что на реальном корпусе из PDF извлечение стало достаточно устойчивым для дальнейшего построения графа и retrieval.

Важно и то, что улучшение достигнуто не сменой всего стека, а исправлением extraction prompt и стабилизацией пайплайна. Для защиты это полезный вывод: основная инженерная работа здесь была не в поиске одной "магической" модели, а в итеративной доводке промптов, схем и контроля ошибок.

### 4.3 Retrieval на живом корпусе

#### Workspace-scoped retrieval

Эксперимент `workspace_scoped_live` проверяет простой, но важный сценарий: если пользователь работает не со всем корпусом, а только с выбранным подмножеством статей, система не должна подтягивать удобные, но запрещённые документы извне.

Результат `forbidden_violation_count=0` на `6/6` кейсах показывает, что это ограничение выдерживается. Отрицательные сценарии также важны: когда в выбранном workspace нет оснований для ответа, система должна корректно отказываться от ответа, а не выдумывать цитату.

#### Hybrid retrieval

Эксперимент `hybrid_ablation_live` устроен так: системе задаются тематические запросы вроде `anchor-free`, `focal loss`, `set prediction transformer`, и проверяется, попадают ли ожидаемые статьи в топ выдачи. На 8 кейсах наблюдается стабильный `hit_count=5/5`, а верхние cosine scores лежат в диапазоне примерно `0.65-0.74`.

Это хороший знак, но здесь важен честный комментарий. На раннем пилотном корпусе прирост hybrid над pure vector retrieval почти не наблюдался (`mrr_delta ≈ 0`). Это не ошибка в таблице, а содержательный вывод: чтобы гибридный поиск начал заметно выигрывать, нужен более разнообразный набор кандидатов. На маленьком корпусе этот эффект может быть слабым.

#### Multi-hop graph retrieval

Эксперимент `multihop_v2` проверяет уже не текстовый retrieval, а способность системы восстанавливать цепочки развития методов через граф. На трёх кейсах получен стабильный `recall≈0.667`.

Этот результат важен именно как подтверждение пользы графа. Одновременно он показывает ограничение текущей реализации: `precision` остаётся низкой (`0.02-0.04`), потому что двухшаговый обход в плотном корпусе вытягивает много лишних соседей. Следовательно, граф полезен как источник структурных кандидатов, но для production-ответа ему всё ещё нужна дополнительная фильтрация или агрегация.

### 4.4 Извлечение утверждений: почему недостаточно простого gold

Если смотреть только на `claims production`, можно сделать слишком оптимистичный вывод: `recall=1.0` на 10 кейсах. Но этот benchmark основан на quote-based gold, где короткая опорная фраза дословно встречается в тексте статьи. Для extraction-задачи это слишком удобная постановка.

Поэтому более важным здесь является эксперимент `claims_paraphrase`, где gold-утверждения перефразированы и ограничены по overlap с исходной статьёй. На нём система показывает:

- pilot: `recall=0.625`, `precision=0.286`;
- holdout: `recall=0.25`, `precision=0.077`.

Это один из самых полезных результатов во всём отчёте. Он показывает, что текущий extractor действительно умеет находить часть содержательных claims, но пока шумит и пропускает нетривиально сформулированные случаи. Для защиты такой результат лучше, чем искусственные `1.0`: он показывает, что benchmark способен различать сильное и слабое поведение.

### 4.5 End-to-end агентный режим

Эксперимент `agent_tools_live` проверяет систему в наиболее близком к пользовательскому режиму сценарии: живой supervisor, живой retrieval, живой граф, финальный ответ с цитатами.

Полученные результаты:

- `10/10` кейсов прошли формальные проверки;
- `latency_p95 = 25 983 ms`;
- средняя LLM-as-Judge оценка качества ответа: `4.8/6`.

Этот результат означает, что система уже работает как целостный pipeline, а не набор разрозненных модулей. В то же время latency около 26 секунд показывает, что production-grade с точки зрения функциональности ещё не равен production-grade с точки зрения UX.

### 4.6 Вторичные, но полезные результаты

Некоторые семейства экспериментов не являются центральными для главного тезиса, но подтверждают согласованность всей системы.

1. **Поиск противоречий.** Все 7 проверочных пар были материализованы как `:CONTRADICTS` связи в графе. Это показывает, что слой claims и граф действительно связаны между собой, а не существуют независимо.
2. **Дедупликация сущностей.** Для 5 типов сущностей получено качество кластеризации `ARI` от `0.88` до `1.00`. Это важно, потому что плохая дедупликация быстро разрушает качество графа знаний: один и тот же метод начинает жить под несколькими именами, а retrieval и traversal становятся менее надёжными.

Эти результаты полезны как подтверждение того, что система работает не только на центральной цепочке "retrieval -> answer", но и на задачах качества данных.

## 5. Обсуждение

### 5.1 Что доказывают результаты

Если смотреть на результаты в совокупности, проект подтверждает три тезиса.

1. **GraphRAG здесь оправдан.** Система поддерживает запросы, которые неудобно решать только векторным поиском: lineage методов, противоречия, graph-aware навигацию по корпусу.
2. **Пайплайн стабилен на реальном корпусе.** Базовые extraction-слои доведены до nightly-состояния без падений.
3. **Оценка не скрывает слабые места.** Как только benchmark становится более строгим, это немедленно видно в метриках, особенно на `claims_paraphrase` и `multihop`.

### 5.2 Почему здесь важны не только высокие метрики

Для внешнего читателя может показаться странным, что в отчёте специально оставлены слабые числа вроде `recall=0.25` или низкой precision у multi-hop retrieval. Но именно это и делает результаты убедительными.

Если все значения идеальны, а benchmark-структура при этом непрозрачна, трудно понять, измеряется ли вообще реальное качество. В данном проекте более низкие метрики играют позитивную роль: они показывают, что benchmark действительно отделяет сложные случаи от простых.

### 5.3 Роль честной оценки

Отдельно стоит подчеркнуть, что часть инженерной новизны проекта лежит не в самой LLM-модели, а в способе проверки результатов. В проект были встроены:

- разделение live и mock режимов;
- явная маркировка `trust_signal`;
- dual/triple validation gold-разметки;
- анти-тавтологические ограничения для части benchmark-наборов.

Для исследовательского software-проекта это существенный вклад. Без таких ограничений итоговые таблицы выглядели бы лучше, но были бы менее надёжными.

## 6. Ограничения

Несмотря на хорошие результаты на части задач, у текущей системы есть явные ограничения.

1. **Доменная узость корпуса.** Все эксперименты проведены на object detection. Это хороший тестовый домен, но он не доказывает переносимость extraction prompt'ов на другие области науки.
2. **Claims extraction пока слабее, чем хотелось бы.** Строгий paraphrase-gold показывает заметную потерю recall и precision.
3. **Multi-hop retrieval нуждается в постобработке.** Recall уже полезен, но низкая precision мешает напрямую использовать графовый обход как готовый финальный ответ.
4. **Judge и extractor частично близки по стеку.** Для production-оценки лучше ещё сильнее разводить модели, которые генерируют ответы и оценивают их.
5. **Latency end-to-end режима заметна для UI.** Система функционально работает, но требует дальнейшей оптимизации маршрутизации и числа LLM-шагов.

Эти ограничения не обнуляют результат проекта, но задают естественный план следующего этапа.

---

## 7. Заключение

В проекте реализована рабочая GraphRAG-система для научного корпуса с тремя ключевыми свойствами: структурное представление знаний, проверяемые ответы с цитатами и честная система оценки.

Главный вывод состоит в том, что граф знаний и маршрутизация между специализированными агентами действительно полезны для исследовательского сценария, но только при условии, что benchmark-программа устроена строго и не скрывает слабые места. В этом смысле проект показывает не только инженерную реализацию, но и методологию оценки таких систем.

На защите имеет смысл делать акцент на трёх тезисах:

1. система работает end-to-end на реальном корпусе статей;
2. она поддерживает типы запросов, которые неудобны для обычного vector-only RAG;
3. её качество оценивается не по удобным smoke-тестам, а по живым и частично "неприятным" benchmark-сценариям.
