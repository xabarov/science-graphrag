## Общая логика выступления

Защиту лучше держать на трёх центральных тезисах:

1. Построена **реальная GraphRAG-система** для корпуса научных статей, а не только экспериментальный прототип.
2. Граф и маршрутизация между специализированными агентами дают пользу там, где обычного векторного RAG уже недостаточно.
3. Проект ценен не только реализацией, но и **честной системой оценки**, которая не скрывает слабые места.

Ниже каждый слайд описан как мини-блок с четырьмя обязательными частями:
- что должно быть на слайде;
- какие артефакты можно вставить;
- что говорить устно;

## Слайд 5. Архитектура и устройство системы

### Заголовок

`Архитектура системы`

### Что должно быть на слайде

На этом слайде нужно показать **главную схему проекта** как две разные фазы, а не как один непрерывный pipeline.

**Фаза 1. Offline ingest / подготовка корпуса**

`PDF / Markdown / Text -> article.md -> extraction pipeline -> Postgres + Neo4j + Qdrant`

**Фаза 2. Online chat / runtime**

`user query -> supervisor -> retrieval_agent / graph_agent / writer_agent -> чтение из Postgres + Neo4j + Qdrant -> answer with citations`

Отдельными короткими подписями стоит зафиксировать:

- почему три хранилища не избыточны;
- почему авторство моделируется через `Authorship`;
- зачем нужен supervisor вместо одного агента.
- что во время чата **ingestion не происходит**: runtime использует уже подготовленные данные.

### Ключевая мысль

Главный инженерный результат проекта — не отдельный модуль, а связанная архитектура из двух контуров: отдельный ingest-конвейер готовит данные, а чатовый runtime работает поверх уже построенных хранилищ.

### Что говорить устно

«Здесь важно не смешивать две разные фазы. Сначала отдельно работает ingest-конвейер: статьи нормализуются, проходят извлечение, и результаты записываются в PostgreSQL, Neo4j и Qdrant. Потом отдельно работает чатовый runtime: пользователь задаёт вопрос, supervisor выбирает, когда нужен retrieval, когда графовый обход, а когда уже можно собирать ответ. Во время чата ingestion не происходит, runtime использует уже подготовленные данные».

### Артефакты

Приоритетные артефакты:

- архитектурная схема с **двумя контурами**: `offline ingest` и `online chat runtime`;
- маленький inset с ролями `PostgreSQL / Neo4j / Qdrant`;
- при желании мини-блок `retrieval_agent / graph_agent / writer_agent`.

Дополнительные ссылки в заметках:

- `docs/architecture/phase-1-backbone.md`
- `docs/adr/005-authorship-reified-node.md`
- `docs/adr/020-langgraph-supervisor-multiagent.md`
- `docs/architecture/observability-phoenix.md`

### Способ производства

Лучше всего: `Nano Banana` или отдельная аккуратная схема  
Если нужно быстро: `HTML` с диаграммой блоков

### Источник содержания

- `2.1 Общая схема`
- `2.2 Почему используется три хранилища`
- `2.3 Графовая модель`
- `2.4 Агентный runtime`

### Что подготовить заранее

- выбрать одну схему, а не 3 конкурирующие;
- убрать технические детали, которые не нужны на защите;
- оставить читаемость при быстром просмотре.
- не показывать ingest и chat как одновременный процесс на одной линии времени.

## Слайд 7. Основные результаты и метрики

### Заголовок

`Основные результаты`

### Что должно быть на слайде

На этом слайде не нужно показывать все таблицы из отчёта. Лучше оставить 4 опорных результата:

1. **Качество извлечения сущностей для GraphRAG**
   - методы: macro F1 около `0.60`
   - датасеты: macro F1 около `0.79`
   - `CITES` в Neo4j: macro F1 около `0.82`

4. **Сквозной агент** — `10/10`, `latency_p95 ≈ 26s`, судья `4.8/6`.

Отдельно: **утверждения по перефразированному эталону** дают слабые цифры — это плюс к честности оценки, не минус к защите.

### Ключевая мысль

Система уже работает на реальном корпусе и даёт убедимые результаты по нескольким линиям, но при этом строгие тесты честно показывают, где остаются ограничения.

### Что говорить устно

«Четыре уровня: извлечение под граф и рёбра цитирования; retrieval на корпусе; многошаговый граф; сквозной агент. Слабые метрики на перефразе утверждений оставляю намеренно — так видно, что контрольные наборы различают “удобный” и строгий эталон».

## Слайды 10–12. Итоги (как в HTML-деке)

Три коротких слайда вместо одного длинного: **бенчмарки → агент/UI → накопленное и планы**. Ниже — сжатый текст для слайда 10 (не дублировать весь отчёт).

### Слайд 10. Выводы по бенчмаркам

**Тезис.** Оценка не сводится к одной галочке «совпало / нет»: для разных полей скрипты бенчмарков (модули `eval/…`) считают разные численные показатели относительно эталона — полнота, точность, текстовое сходство и т.д.

**Каркас статьи.** Заголовок, абстракт, авторы и выборка идентификаторов в библиографии измеряются отдельными метриками (в т.ч. текстовые и по множествам); детали — в отчёте и в коде `eval/layer1/`, без зачитывания на слайде.

**Утверждения, концепты, темы.** Полнота и точность считаются с несколькими режимами сопоставления с эталоном (в т.ч. перефраз); не перечислять на слайде все ветки — достаточно сказать устно: «режим и порог задаются в gold кейса».

**Методы и датасеты для графа.** Мягкое совпадение нормализованных имён и алиасов, порог уверенности модели; для длинных названий — допуск по пересечению слов с эталоном (`eval/layer2/`).

**Список литературы.** Отдельный bench по секции References (overlap по записям и границы секции) — упомянуть одной фразой как про «самый шумный слой».

**Закрывающая фраза.** В отчёте и устно важно называть, *какой* режим сравнения сработал и *какие* пороги — иначе цифра без контекста мало что говорит.

### Слайд 11. Агент, трассировка, интерфейс

- без цепочки шагов агента ответ оценивать почти бессмысленно;
- трассировка — не декор, а разбор спорных прогонов;
- финальный шаг ответа и большой граф в UI — известные хрупкие места; бенчмарки их подсвечивают.

### Слайд 12. Накопленное и планы

- что уже есть: сквозной путь, разделение сигналов, связка UI ↔ «под капотом»;
- куда: tool search по смыслу, уплотнение контекста, точность графа/утверждений, корпус и инженерия отрисовки графа;
- одна итоговая цитата из отчёта при желании.
