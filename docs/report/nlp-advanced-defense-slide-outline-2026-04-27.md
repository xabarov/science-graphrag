# Текст к слайдам (защита NLP Advanced)

Источник цифр и развёрнутой методики: `docs/report/nlp-advanced-final-report-2026-04-26.md`. Дек: `docs/report/nlp-advanced-defense-slides.html` (12 слайдов).

---

Слайд 1. Титульный

Интеллектуальная система поддержки научного исследования на основе GraphRAG. Курс NLP Advanced. Это не просто чат над документами: исследовательская система для корпуса статей — структура знаний в графе, цитаты, трассируемость шагов агента и честная оценка качества (бенчмарки). Подзаголовок: GraphRAG, агентный поиск и проверяемые ответы по научным статьям.

---

Слайд 2. План защиты

Пять блоков: цель и задачи проекта; какие технологии использовались; что получилось на практике — архитектура, агент, артефакты, ключевые метрики и демо; выводы и ограничения; вопросы и направления развития. Основная часть — середина: реализация и результаты, а не только постановка задачи.

---

Слайд 3. Цель и задачи проекта

Цель: сквозная GraphRAG-система для исследователя над связным корпусом статей — граф знаний, retrieval и ответы с цитатами. Задачи: нормализовать статьи и извлечь структуру для графа; построить граф и векторный поиск; поддержать текстовый и графовый доступ к данным; синтезировать ответы с обязательными цитатами; оценивать систему так, чтобы метрики отражали реальное качество, а не «удобный» срез.

---

Слайд 4. Какие технологии использовались

Стек по ролям: Python, FastAPI и агентный runtime (LangGraph) для backend. Три хранилища — PostgreSQL (операционное состояние и артефакты пайплайна), Neo4j (граф знаний и структурные запросы), Qdrant (семантический поиск по чанкам). NLP/LLM: извлечение сущностей и связей, эмбеддинги, tool-calling. Интерфейс: React; наблюдаемость — Phoenix / OpenTelemetry. Оценка: бенчмарки в `eval/`, формальные проверки сценариев агента, при необходимости дополнительная валидация прогонов.

---

Слайд 5. Архитектура системы

Два контура, не один поток: offline ingest готовит корпус (нормализация, извлечение, запись в Postgres + Neo4j + Qdrant); online runtime отвечает на вопросы пользователя только по уже подготовленным данным — во время чата ingestion не крутится. Phase 2 на схеме — Agent Runtime: один research-агент с набором tools к трём хранилищам (не три независимых субагента по умолчанию). Опционально в конфиге — supervisor с отдельными нодами. Авторство в графе вынесено в явную модель (узел authorship). Итог: связанная архитектура ingest и чата, а не набор разрозненных сервисов.

---

Слайд 6. Инструменты агента и системный промпт

Режим `langgraph_research_v1`: модель видит каталог из девяти инструментов — имена, короткие описания и схему аргументов (как у структурированного tool-calling). Слои: graph (`cypher_query`, `edge_search`), каталог работ (`workspace_inspect`, `paper_profile`, `find_works`, `format_bibliography_gost`), evidence (`paper_quote_search`, `idea_search`), завершение хода (`final_answer` с markdown и списком citations). В системном промпте зафиксированы scope (только evidence из workspace, не выдумывать DOI и метрики), таблица маршрутизации «какой вопрос — какой тул», ограничение фан-аута и обязательный один вызов `final_answer` в конце хода.

---

Слайд 7. Те же тулзы как Python-функции

Идея для аудитории: сигнатура функции и docstring — это тот же контракт, что видит модель (имя инструмента, параметры, семантика возврата), в духе smolagents / Pydantic-схем. На слайде — укороченные примеры для `paper_quote_search`, `cypher_query`, `find_works`: видно границы ответственности (семантика по чанкам, read-only Cypher, полнотекст по работам).

---

Слайд 8. Демонстрация системы

Один сценарий: исследовательский вопрос по корпусу → цепочка вызовов тулов (retrieval и/или граф) → ответ с цитатами; при желании в кадре — trace в UI. Смысл: архитектура и таблицы метрик подтверждаются живым прогоном, а не только отчётом. Ответ строится по корпусу: evidence, цитаты на статьи, трассировка шагов.

---

Слайд 9. Основные результаты и выводы

Срез по отчёту: качество извлечения под граф (методы, датасеты, рёбра CITES), retrieval на корпусе, многошаговый обход графа (высокий recall при слабой precision — много лишних соседей), сквозной агент (формальные проверки suite, задержка p95, оценка судьёй). Слабые цифры на утверждениях с перефразированным эталоном оставлены намеренно: они показывают разницу между «удобным» и строгим контролем качества.

---

Слайд 10. Выводы по бенчмаркам

Оценка извлечения и постановки графа не сводится к одной галочке: для разных полей в `eval/` считаются разные числа относительно эталона — точное совпадение после нормализации, меры текстового сходства, P/R/F1 по множествам идентификаторов, IoU по строкам для библиографии, отдельные режимы для перефраза утверждений. Для методов и датасетов — мягкое сопоставление нормализованных имён и алиасов с порогом уверенности модели и допуском по пересечению слов на длинных названиях. Список литературы — отдельный контур: шум PDF, границы секции References, overlap записей. Подробная расшифровка метрик — в справке ниже; при ответах на вопросы всегда называть режим сравнения и пороги из gold кейса.

---

Слайд 11. Агент, трассировка, интерфейс

Оценка ответа без цепочки шагов почти бессмысленна: правдоподобный текст не заменяет проверку, куда агент ходил и не оборвал ли сценарий. Трассировка в UI показывает, завершён ли сценарий аккуратно. Обязательный `final_answer` чувствителен к смене промпта и графа — это ловит сквозной бенчмарк. Отдельная тема: отрисовка большого графа в браузере — даже корректные данные не гарантируют читаемую картинку без доработок UX.

---

Слайд 12. Накопленное и дальнейшие планы

Уже есть: путь от корпуса до ответа с источниками; разделение сигналов (извлечение, retrieval, граф, агент); связка того, что видит пользователь, с тем, что произошло под капотом. Дальше: подбор инструментов по смыслу (tool search), уплотнение контекста в длинных диалогах, точность утверждений и многошагового графа, снижение задержки, расширение корпуса и доменов, инженерия визуализации графа. Итог ценен и собранным конвейером, и явной фиксацией трудностей (валидация, литература, агент, UI) с планами, которые эти места не заметают.

## Справка к слайду «Выводы по бенчмаркам»: метрики по извлекаемым полям

Ниже — как в коде `eval/` устроены метрики, чтобы отвечать на вопросы вида «какие меры сходства?» и «что именно считается по полю X?». Везде важно: **какой режим матчинга** (exact / token / ROUGE / эмбеддинг / множество / IoU) и **какой порог** задаются в gold кейса или в профиле порогов (`eval/layer1/threshold_profiles.py`, поля в `gold.json`).

### Общие приёмы (словарь)

- **Точное совпадение после нормализации** — пробелы, регистр, часть пунктуации; для части полей — дополнительная нормализация (например DOI через `normalize_doi`).
- **Меры текстового сходства** (реализация в `eval/layer1/text_similarity.py`, без тяжёлых внешних библиотек):
  - **ROUGE-L F1** (по словам): доля совпадающей «кости» текста через длину наибольшей общей подпоследовательности токенов; хорошо для заголовка и для сравнения короткого эталона (prefix абстракта) с длинным извлечённым абстрактом; для длинных текстов может обрезаться по `max_words` ради стабильности.
  - **Multiset token F1** — пересечение счётчиков токенов между эталоном и гипотезой, затем стандартные precision/recall/F1 по этим пересечениям; устойчив к перестановке слов, хуже ловит перефраз целиком.
  - **Token containment для prefix абстракта** — какая доля токонов из эталонного префикса встречается в полном абстракте; запасной путь против PDF→MD дрейфа, когда строгое «startswith» ломается, но смысл префикса сохранён.
  - **difflib macro по авторам** — для каждого эталонного ФИО берётся лучший `SequenceMatcher.ratio` к любому предсказанному имени, затем среднее; мягче жёсткого множества строк, но может «простить» заметные ошибки.
- **Пересечение множеств идентификаторов** — для подмножества ссылок в библиографии: из предсказанных `ReferenceDraft` собираются множества arXiv id и DOI (в т.ч. regex из сырого текста ссылки), эталон — `sample_arxiv_ids` / `sample_dois` в gold; далее классический **micro P/R/F1 по множествам** (`tp`, `fp`, `fn` как размеры пересечений и разностей) — функция `prf1_tp_fp_fn` в `eval/layer1/metrics.py`.
- **P/R/F1 по множеству имён авторов** — имена нормализуются как строки в нижнем регистре схлопыванием пробелов; множество эталонных vs множество предсказанных; отдельно считаются порядок (доля позиций, где имя совпало с эталоном в той же позиции), **Jaccard по аффилиациям** для спаренных по имени авторов, плюс плоское множество всех аффилиаций для aggregate F1.
- **IoU по множествам номеров строк** — для локализации секции References в `article.md`: пересечение множеств строк эталона и предсказания / объединение (`eval/references_harness/metrics.py`), с оговоркой, что gold-диапазон может расширяться на строку заголовка `## References` для честного сравнения с эвристиками.
- **Overlap записей библиографии** — greedy many-to-one: каждая эталонная запись матчится не более чем с одной предсказанной с лучшим **Jaccard по токенам** строки; порог по умолчанию 0.35; из матчей считается micro precision/recall/F1 (`entry_overlap_micro_f1`).

### По полям / слоям (что считается и зачем так)

| Область | Что в эталоне | Что считается | Зачем выбрано |
|--------|----------------|---------------|----------------|
| Заголовок, год, тип работы, DOI/arXiv на карточке статьи | Поля в `work_metadata` | Exact после нормализации; для заголовка дополнительно ROUGE-L и token F1 как диагностика | Exact — строгий контракт для библиографии и графа; ROUGE/token — не обанкротить прогон из-за мелкой пунктуации или стиля |
| Абстракт | Часто `abstract_prefix` | Префикс как подстрока после нормализации дефисов/кавычек; плюс ROUGE-L префикса к полному тексту; containment токенов | Префикс дешевле полного gold всей статьи; containment ловит типичный шум PDF |
| Авторы и аффилиации | Списки в gold | Имена: set P/R/F1, order accuracy, difflib macro; аффилиации: Jaccard на парных авторах + flat set F1 | Набор имён — для графа authorship; порядок — для библиографического вида; difflib — запасной мягкий сигнал |
| Число ссылок | `expected_count`, `min_count` | Попадание в диапазон (в т.ч. мягкий множитель в `quality_thresholds`) | PDF даёт разброс длины списка; жёсткий «ровно N» часто ложный fail |
| Подвыборка arXiv/DOI в списке литературы | `sample_arxiv_ids`, `sample_dois` | Set P/R/F1 по извлечённым идентификаторам | Проверка, что «якорные» работы пойманы, без ручного разбора всего списка |
| Секция References (уровень A/B) | Строки span, `raw_entries` | IoU строк; entry overlap micro-F1 | Разделяет «где секция» и «насколько похожи строки записей» |
| Методы и датасеты (semantic layer2) | Имена в gold | Нормализация, отбор предсказаний по `confidence_threshold`, матч: exact, вложенность короткой строки в длинную (с ограничениями длины), для длинных фраз — word Jaccard ≥ 0.55 | Ночной семантический слой даёт вариативные строки; нужен устойчивый fuzzy-match без полного NLI |
| Утверждения (claims) | `expected_claims`, режимы в gold | Базово: recall/precision по `claim_id`; режим `claim_id_or_normalized_text` — якорная подстрока в тексте предсказания; для перефраза в строке gold — `exact` / `rouge_l` / `embedding_sim` с порогами | Строгий id — для регрессий пайплайна; перефраз — для ближе к пользовательской формулировке; эмбеддинг дороже, но ловит семантику |
| Концепты и темы | id + `anchor_phrase` | Сначала id, иначе вхождение anchor в «blob» предсказания; своя precision по покрытию предсказаний | Аналогично claims: баланс строгости и покрытия перефраза |

### Что выбрано спорно / слабые места (задел)

- **Multiset token F1 и ROUGE-L** не эквивалентны человеческой оценке перефраза; для «научного» текста лучше бы иметь отдельную human eval или NLI/эмбеддинг-ранжирование на ключевых полях — сейчас это точечно только в claims при явном `match_mode`.
- **difflib по авторам** может завысить совпадение при частичных строках; компенсируется жёстким set-F1 в порогах, но комиссиям стоит смотреть оба числа.
- **Layer2 methods/datasets** — эвристический fuzzy-match; пограничные кейсы (синонимы без пересечения слов) останутся false negative без словаря или LLM-судьи.
- **Sample arXiv/DOI** — не полное сравнение всей библиографии, а подмножество; полный pairwise по всем ссылкам дорог и шумно на PDF.
- **Embedding в claims** зависит от модели эмбеддингов и порога; пороги в gold нужно калибровать по валидации, иначе метрика «плавает» между прогонами.

Если спрашивают «какая у вас метрика по полю P» — ответ по шаблону: **имя поля в gold → режим сравнения → агрегат (precision/recall/F1 / IoU / ROUGE)** → **порог из кейса**, плюс ссылка на модуль (`eval/layer1/metrics.py`, `eval/layer2/metrics.py`, `eval/claims/metrics.py`, `eval/references_harness/metrics.py`, `eval/concept_topic/metrics.py`).
